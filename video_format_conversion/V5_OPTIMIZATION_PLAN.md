# 视频格式转换工具 v5 优化方案

## 一、四个版本的优缺点分析

### v1 (main.py) - 基础版 (426行)
| 优点 | 缺点 |
|------|------|
| 代码简洁，结构清晰，易于理解 | 无批量处理能力 |
| CLI + GUI 双模式完整可用 | 无进度跟踪，用户需盲等 |
| 启动快速，依赖最少 | 仅支持6种格式 |
| 错误处理逻辑直观 | 类型提示不完整 |
| | 无预设管理，每次手动设置参数 |
| | 无视频信息预览 |

### v2 (main_v2.py) - 增强版 (1433行)
| 优点 | 缺点 |
|------|------|
| 功能全面：批量转换、进度跟踪、预设管理 | 代码量过大(1433行)，维护成本高 |
| 完整类型系统和完善文档字符串 | 批量处理为串行执行，效率低下 |
| 编解码器支持大幅扩展(7视频+5音频) | GUI界面复杂，学习曲线陡峭 |
| 结构化日志系统 | 部分功能未完整实现(`_add_current_as_preset`等为空) |
| 8种格式支持 | 日志回调仅在error/warning时触发，信息不完整 |
| | 进度解析仅从stderr读，且stdout被合并到stderr |

### v3 (main_v3.py) - 优化版 (1694行)
| 优点 | 缺点 |
|------|------|
| 并行批量转换(ThreadPoolExecutor) | 代码量最大(~1694行)，结构冗长 |
| 拖拽文件支持 | DragDropEntry依赖tkinter-dnd外部库 |
| 视频信息预览(ffprobe) | ffprobe调用超时设置为30秒过长 |
| 更精确的进度计算(基于视频时长) | CRF滑块与Spinbox双向绑定可能冲突 |
| 中文界面本地化 | 批量进度在并行模式下更新不准确(每次都创建新的ConversionProgress) |
| "copy"编解码器选项(免重新编码) | 编码器选择UI用了名称字符串而非枚举值，转换逻辑脆弱 |
| 编码速度实时显示 | 批量转换时无整体进度条更新 |

### v4 (main_v4.py) - 平衡版 (1280行)
| 优点 | 缺点 |
|------|------|
| 自适应并行调度(基于CPU/内存) | **严重性能Bug**: `convert_video`在stdout循环内每行输出都调用`get_video_info()`(即每行调一次ffprobe)，极其低效 |
| 简化GUI降低复杂度 | GUI去掉了批量转换标签页和预设标签页，功能退化 |
| 递归目录扫描 | `AdaptiveParallelScheduler`在类定义时就尝试`import psutil` |
| 良好的向后兼容性 | 去掉了v3的"copy"编解码器选项 |
| CLI支持逗号分隔文件列表 | GUI不支持拖拽，去掉了进度条 |
| 添加了恢复机制(KeyboardInterrupt) | 无字幕处理、无音频提取、无硬件加速 |
| | 线程为daemon模式，无法取消正在进行的转换 |

## 二、v5 优化思路

### 2.1 修复关键缺陷 (P0)

#### Bug #1: v4进度跟踪中重复调用ffprobe
- **问题**: `convert_video`在stdout输出循环的每一行都调用`get_video_info(input_path)`，每次调用启动一个ffprobe进程，导致转换速度严重下降
- **修复**: 在循环外获取一次视频时长，缓存结果

#### Bug #2: 线程无法取消
- **问题**: 所有版本的转换线程都是daemon线程，无法主动取消正在进行的转换
- **修复**: 使用`subprocess.Popen`的`terminate()`方法，配合取消标志实现可中断转换

#### Bug #3: 并行批量进度不准确
- **问题**: v3在item_complete_callback中每次都创建新的ConversionProgress对象
- **修复**: 使用共享的进度对象和线程锁，确保顺序更新

### 2.2 硬件加速支持 (P1)
- **自动检测**: 检测NVIDIA NVENC、Intel QSV、AMD AMF编码器可用性
- **智能选择**: 根据硬件能力自动选择合适的硬件编码器
- **用户可选**: CLI/GUI提供手动切换硬件/软件编码的选项
- **性能提升**: 硬件编码通常比软件编码快2-5倍

### 2.3 流复制优化 (P1)
- **智能判断**: 当源格式和目标格式容器兼容且编解码器相同时，自动使用`-c copy`流复制
- **无损快速**: 流复制不解码/编码，速度极快且无质量损失
- **适用场景**: 例如MKV→MP4容器转换（H264流兼容时）

### 2.4 新增功能特性 (P1-P2)

#### 字幕处理
- 自动检测并复制字幕流到输出文件
- 选项：保留所有字幕、仅保留指定语言、跳过字幕

#### 音频选项
- 提取音频为独立文件(mp3/aac/wav等)
- 移除音频轨道(静音视频)
- 音频音量归一化

#### 分辨率缩放
- 指定输出分辨率(如1920x1080、1280x720)
- 保持纵横比缩放
- 预设常用分辨率

#### 视频片段截取
- 支持`--start`和`--duration`参数截取片段
- 快速seek定位

### 2.5 架构改进 (P1)

#### 任务管理系统
- **任务队列**: 支持添加、暂停、恢复、取消任务
- **并发控制**: 可配置最大并行任务数
- **状态跟踪**: pending → running → completed/failed/cancelled

#### 转换历史
- **SQLite存储**: 记录每次转换的参数、结果、耗时
- **查询功能**: 按日期、格式、状态查询历史
- **统计信息**: 累计转换次数、成功率、节省空间等

#### 懒加载优化
- psutil等可选依赖仅在需要时导入
- 硬件加速检测在首次转换时执行并缓存结果

### 2.6 GUI改进 (P2)
- **恢复标签页设计**: 单文件/批量/预设三个标签页
- **批量进度可视化**: 每文件独立进度条
- **拖拽支持**: 使用内建方式实现(或不依赖外部库的简单实现)
- **实时编码速度显示**: 在状态栏显示当前编码速度

## 三、v5 实现计划

### 核心原则
1. **修复优于新增**: 先修复v4的关键bug
2. **质量优于数量**: 控制代码行数在合理范围(目标~1000行)
3. **模块化但不拆分**: 保持单文件但内部结构清晰
4. **向后兼容**: 保持v1的CLI接口兼容

### 实现内容

#### Phase 1: 核心修复与优化
- 修复进度跟踪中的ffprobe重复调用
- 实现可取消的转换
- 优化并行批量进度跟踪
- 懒加载psutil

#### Phase 2: 硬件加速
- 检测NVENC/QSV/AMF
- 硬件编码器自动选择逻辑
- CLI/GUI硬件加速开关

#### Phase 3: 新功能
- 字幕处理(保留/跳过/提取)
- 音频模式(正常/仅音频/静音)
- 分辨率缩放
- 视频片段截取
- 流复制智能优化

#### Phase 4: 架构增强
- 任务管理系统
- SQLite转换历史
- GUI标签页恢复
- 批量进度可视化

### 预期效果
- **性能**: 硬件加速可提升2-5倍编码速度
- **可靠性**: 可取消转换 + 更好的错误处理
- **功能**: 字幕、音频、缩放、截取等实用功能
- **可用性**: 转换历史、任务管理提升使用体验
- **代码**: 目标1000-1200行，保持可维护性
